# The contract

`api/openapi.yaml` describes every REST endpoint and every synced item type, and both
sides are generated from it: the server's Spring interfaces and DTOs, the app's Dart
client. **The contract is the source** — an endpoint or a field exists when it is in
the contract, not when one side happens to send it.

```
api/
  openapi.yaml            the root: info, tags, servers, and the $refs to the parts
  paths/<module>.yaml     the endpoints, one file per server module
  components/<module>.yaml  the schemas, one file per module (errors.yaml: the error model)
  openapi.bundled.yaml    generated: the parts resolved into one file
```

The bundled file is checked in: it is what the Dart generator reads (it does not
follow references to other files), and after a release it becomes the baseline the
next changes are checked against.

## Changing it

```sh
# 1. edit api/paths/*.yaml and api/components/*.yaml
cd server && ./gradlew :api:updateBundledSpec     # resolve the $refs
./gradlew build                                   # server: regenerate, compile, check
cd ../app
dart run swagger_parser                           # client: regenerate
dart run build_runner build --delete-conflicting-outputs
```

Whoever forgets a step notices at compile time — that is the point. Commit the changed
parts and `openapi.bundled.yaml` together.

- **Server**: a controller `implements` the generated interface (`<Tag>Api`) and works
  with the generated DTOs. Generated code is never edited.
- **Client**: the generated clients live in `app/lib/core/api/generated/` (not checked
  in). Two tags are excluded from generation in `app/swagger_parser.yaml` — `images`
  and `backupFiles` — because the generator maps a binary body to `dart:io File`, which
  does not compile for the web; their calls are written by hand
  (`core/api/image_client.dart`, `core/api/backup_file_client.dart`) against the same
  endpoints. The server side of those tags is generated as usual.
- **The home screen widgets** have native clients of their own, reduced to the two calls
  they make (`getAgenda`, `getListSummary`): Kotlin, generated by the Android Gradle build,
  and Swift, generated by `app/tool/generate_widget_client.sh`
  ([`home-widgets.md`](home-widgets.md)). Neither is checked in.
- Descriptions in the contract are documentation for both sides: say what a field means
  and what the server does with it, in English.

## Compatibility is checked

An installed app can be older than the server, and nobody updates every device at once.
So the contract only grows:

- New fields are **optional**. Never rename a field, change its type or meaning, or make
  it `required` afterwards.
- **Enums are only extended.** The client survives an unknown value
  (`unknown_enum_value: true` in the generator config maps it to a placeholder). The
  widgets' Swift and Kotlin clients would not: the schemas they read carry no enums, only
  strings.
- Nothing is removed without a deprecation period. A real break would be `/api/v2`.

The build checks this against `api/openapi.baseline.yaml`, the last **published**
contract, in two tasks hooked onto `check`:

| Task | Checks |
| --- | --- |
| `checkSpecCompatibility` | `openapi-diff --fail-on-incompatible`: what breaks a caller |
| `checkSpecContract` | `SpecContractTask` (`buildSrc`): what breaks a *reader* — `openapi-diff` judges from the caller's side and lets a renamed or removed response field through, but the app reads those responses. No field disappears, none changes its type, nothing becomes required, enums only grow. |

Both say in plain text which spot breaks. Their rules are tested on a miniature contract
in `buildSrc/src/test`.

**The baseline moves only at a release** (`./gradlew :api:acceptSpecBaseline`, see
[`../releasing.md`](../releasing.md)). A baseline every build drags along checks
nothing. Before the first release there is no baseline, and both tasks are skipped.

## Conventions

- **Paths** are `/api/v1/<area>/…`, plural nouns, ids as `{id}` or `{<thing>Id}`.
  `operationId`s are verbs in camelCase (`createInvitation`) — they become method names
  on both sides.
- **Tags** match server modules; each tag becomes one generated interface.
- **Errors** are `ApiError` (`code`, `params`, `correlationId`). Document every error
  code an endpoint can answer in its description, with its HTTP status: `400` invalid,
  `401` not signed in, `403` not allowed, `404` missing **or not visible**, `409`
  conflict, `413` too large, `429` too often. A `403` for something the caller may not
  see would confirm that it exists.
- `ApiError` is listed under `components.schemas` in the root file explicitly: a schema
  no endpoint references is not generated. (It is not called `Error`: the generated Java
  class would shadow `java.lang.Error`.)
- **Synced item types** are schemas too (`components/sync.yaml` and the modules' files):
  the fields as they travel in a push or pull. The envelope is typed; `fields` is
  free-form and decoded per `entityType`.
- **Authentication** is a bearer device token (`Authorization: Bearer …`). Public
  endpoints (`handshake`, `auth/login`, an invitation's preview, the dashboard by its
  token) say `security: []`.

## Outside the contract

| Endpoint | Why |
| --- | --- |
| `GET /api/v1/events?ticket=…` | a server-sent event stream; OpenAPI cannot express it in a way either generator turns into a usable signature. The ticket endpoint is in the contract. |
| `GET /ics/{token}.ics` | a calendar feed for other calendar programs, plain `text/calendar` |
| `/` and the web app's paths | the served Flutter web build |
